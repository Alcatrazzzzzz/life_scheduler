# 007 — Вложения к записям расписания

**Дата:** 2026-11-19
**Статус:** принято

## Контекст

К записям расписания понадобилось прикладывать файлы: без документов и фото прошедшее
дело не оставляет подтверждения. Проект домашний, один разработчик, SQLite и один
пользователь, но хранилище должно пережить переход на удалённый S3 без переписывания
фичи. Вложения относятся к записи целиком — так же, как текущая модель повторов.

## Решение

- Метаданные — в SQLite (`ScheduleAttachments`: имя, MIME, размер, ключ, статус),
  сами файлы — в S3-совместимом хранилище.
- Драйвер выбирается конфигом: S3 в боевом режиме, локальный диск
  (`App_Data/attachments`) в dev и тестах; интерфейс `IFileStorage` один.
- Браузер грузит файл напрямую по presigned PUT; API выдаёт тикет, затем подтверждает
  загрузку HEAD-проверкой и только после этого делает вложение `Ready`.
- Лимиты: 25 МБ на файл, 10 файлов и 100 МБ на запись, любые MIME-типы. Вложения
  принадлежат серии повторов целиком.
- Файлы добавляются и в форме создания (после создания записи), и в деталях записи.
- Фича — отдельный срез `Features/Attachments/`; общая сущность `ScheduleAttachment`
  лежит в `Shared/Data/`, как и `ScheduleEntry` (см. ADR 001).

## Альтернативы

- **BLOB в SQLite** — база пухнет, большие файлы хуже дружат с EF и SQLite.
- **Content-addressed хранилище** — дедупликация не окупает сложность на домашних объёмах.
- **Загрузка через API-прокси** — весь трафик идёт через сервер; presigned проще и не грузит API.
- **Вложения на конкретное вхождение серии** — нужна отдельная сущность `Occurrence`, пока не требуется.
- **Жёсткий лимит размера в presigned PUT** — SigV4 PUT не умеет `content-length-range`;
  размер проверяется HEAD-ом после загрузки.
- **Хранить имя файла в ключе объекта** — ключ становится зависимым от Unicode и требует
  санитизации; имя передаём через `Content-Disposition`, ключ обезличен.

## Последствия

- **Плюс:** SQLite остаётся маленькой; файлы живут в S3, локально — на диске.
- **Плюс:** загрузка не идёт через API; метаданные и объект подтверждаются явным `confirm`.
- **Плюс:** один интерфейс хранилища — dev работает без облака, боевой режим переключается конфигом.
- **Минус:** presigned PUT не гарантирует размер до загрузки; при расхождении объект
  удаляется после HEAD, но клиент успевает занять место.
- **Минус:** S3 требует бакет, креды и CORS на `PUT`; боевой путь не проверяется локальными тестами.
- **Минус:** удаление объектов best-effort — при сбое хранилища возможен осиротевший файл;
  полной сверки «БД ↔ бакет» нет.

## Когда пересмотреть

- Понадобятся файлы на конкретное вхождение серии — появится `Occurrence`.
- Понадобится жёсткий лимит до загрузки — presigned POST-policy или прокси.
- Понадобится несколько пользователей/арендаторов — ключи, политики бакета и права.
- Понадобятся превью, антивирус или дедупликация.
