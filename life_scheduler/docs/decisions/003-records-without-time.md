# 003 — Записи без времени в планировщике

**Дата:** 2026-11-17
**Статус:** принято

## Контекст

Изначально запись расписания состояла из даты и обязательного интервала `Start`–`End`.
В реальном использовании значительная часть дел — это «сделать в течение дня»: я знаю,
в какой день нужно заняться делом, но не знаю, во сколько именно. Требовать время
заставляет либо выдумывать его, либо заводить запись в другом месте. Проект домашний,
один разработчик, SQLite; в таблице уже есть записи с валидным временем, которые
нельзя терять.

## Решение

`Start` и `End` становятся nullable (`TimeOnly?`) в сущности, API и миграции; оба `NULL`
означают «дело на день без конкретного времени». Отдельного флага нет — инвариант
«либо оба времени заданы, либо оба пусты» проверяется на границе API и возвращается
как `ValidationProblem`. В рамках дня записи без времени сортируются раньше записей
с временем; в форме это явный чекбокс «Без времени», а не пустые поля.

## Альтернативы

- **Флаг `IsAllDay` + nullable времена** — два источника правды, которые нужно держать
  согласованными; отдельный bool ничего не добавляет к `Start is null`.
- **Дефолтные 00:00–23:59** — неотличимо от настоящего события на весь день, ломает
  семантику `End > Start` и сортировку; намерение «времени нет» теряется.
- **Отдельная сущность для задач дня** — два CRUD-потока для одного экрана; оправдано,
  только если у задач появятся свои поля (дедлайн, приоритет, статус).
- **Пустые поля времени = без времени (без чекбокса)** — меньше разметки, но
  неочевидно: пользователь не понимает, допустима ли пустота, пока не попробует.

## Последствия

- **Плюс:** можно зафиксировать дело на день, не выдумывая время; сортировка внутри
  дня ставит «вне сетки» наверх, где их видно первыми.
- **Плюс:** изменение схемы минимально — две nullable-колонки; существующие данные
  не мигрируют (EF на SQLite пересобирает таблицу, это отработано).
- **Минус:** nullable-время появляется во всех ответах и клиентах; любой новый
  потребитель API обязан различать `null` и «00:00».
- **Минус:** правило «без времени сверху дня» продублировано в эндпоинте и в сортировке
  кэша TanStack Query — менять нужно в двух местах синхронно.
- **Минус:** частично заданное время (только `Start`) отклоняется с 400; UI обязан
  отправлять оба поля `null` или оба значения.
- **Минус:** у записи без времени нет длительности — будущая сетка/календарь должна
  решить, куда её класть, отдельно от алгоритма раскладки интервалов.

## Когда пересмотреть

- У дел дня появятся признаки задачи (статус, приоритет, дедлайн) — тогда нужна
  отдельная сущность или поле, а не `NULL`-время.
- Понадобятся повторяющиеся события или часовые пояса — `DateOnly`/`TimeOnly` перестанут
  описывать модель, потребуется `DateTimeOffset` или правила recurrence.
- Появится второй клиент/пользователь — правило сортировки и контракт `null` нужно
  зафиксировать в API-документации, а не только в коде эндпоинта.
