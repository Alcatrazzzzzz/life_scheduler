# 001 — Vertical slices вместо Clean Architecture

**Дата:** 2026-11-15
**Статус:** принято

## Контекст

Один разработчик, два домашних проекта (планировщик и цифровой мозг), которые
позже сольются. Ожидаемый рост — десятки срезов, не сотни. Команды нет, ревью нет,
ценеремоний нет. Основная боль — навигация по коду и скорость добавления фич,
а не гибкость замены инфраструктуры.

## Решение

Каждый feature — папка в `src/Features/{Feature}/`, внутри которой endpoint, модели
запроса/ответа, handler и валидация. Никаких слоёв controller/service/repository
между фичами. Cross-cutting код — в `src/Shared/`.

## Альтернативы

- **Слоистая архитектура** — одна фича размазана по 5–6 папкам, лишняя навигация
  для одного разработчика.
- **Clean Architecture** — платим структурой за гибкость замены БД/фронта,
  которой не планируем.
- **Modular monolith** — надмножество vertical slices; группировать пока нечего,
  вернёмся при слиянии двух проектов.

## Последствия

- **Плюс:** чтобы понять фичу — открываешь один файл.
- **Плюс:** удаление фичи = удаление папки.
- **Плюс:** меньше файлов на фичу → меньше контекста для Claude Code на задачу.
- **Минус:** cross-cutting код нужно дисциплинированно держать в `src/Shared/`.
- **Минус:** мелкие DTO дублируются между срезами; выносить в `Shared/` — только
  после второго-третьего повторения.

## Когда пересмотреть

- Появился второй разработчик с разделением зон ответственности.
- Срезов стало настолько много, что `src/Features/` нуждается в группировке.
- При слиянии планировщика и цифрового мозга — вероятно, переход к modular monolith
  с модулями `Schedule` и `Memory`.
