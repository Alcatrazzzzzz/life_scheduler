## Что можно сделать

**1. Оставить текущий путь (рекомендую на сейчас)**
`UseGrammar=false`: строгий system prompt + извлечение JSON + валидация + один retry. Уже проверено live: `log_habit`, `list_habits`, `create_habit`, `create_schedule`, `unsupported`, плюс аудио «Отметь зарядку» → Whisper → `log_habit`. Это не «без структуры»: структура обеспечивается промптом и валидацией, просто не грамматикой. Дешевле всего и уже работает.

**2. Дешёвый эксперимент: другой GGUF-токенизатор**
Возможно, баг специфичен для Qwen BPE. Стоит прогнать ту же GBNF с `Phi-3.5-mini-instruct` или `Llama-3.2-3B` GGUF. Если кириллица с грамматикой заработает — просто меняем модель и включаем `UseGrammar=true`, ничего больше не трогаем. Это ~20 минут и ~2 ГБ загрузки.

**3. Основная in-process альтернатива: ONNX Runtime GenAI**
`Microsoft.ML.OnnxRuntimeGenAI` 0.20.0 — NuGet, CPU, без сервера. В нём есть `GeneratorParams.SetGuidance(...)` (llguidance) для constrained decoding; `SetJsonSchema` в 0.20 нет, но JSON описывается Guidance-грамматикой. Модели: ONNX-конверсии Qwen2.5-3B или Phi-3.5-mini.
- Плюсы: строгая грамматика, Unicode-aware движок, полностью локально.
- Минусы: нужно переписать `LlmFunctionCaller`, скачать/подготовить ONNX-модель, замерить латентность и RAM; это уже не GBNF, а Guidance.

**4. Ждать/подтянуть свежий llama.cpp**
Upstream активно правит грамматику (multi-token matching, UTF-8). LLamaSharp 0.30 — последняя на NuGet; можно собрать llama.cpp master и подменить native DLL, но это хрупко и не гарантирует фикс.

**5. Серверные варианты** — Ollama, LM Studio, `llama-server`, vLLM. Грамматику и JSON они умеют, но нарушают ваше требование «никаких внешних серверов», поэтому не рекомендую.

## Итог

Оставил бы текущий prompt+parse+retry как рабочее решение. Если строгий JSON обязателен, порядок такой: сначала проверить Phi-3.5/Llama-3.2 GGUF с той же GBNF, затем — прототип ONNX Runtime GenAI с Guidance. Могу прогнать любой из этих вариантов: скачать модель и сделать минимальный тест на кириллице.
