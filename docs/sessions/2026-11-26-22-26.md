## 3. Выводы по вашим приоритетам

**1. `llm_ms > 15 с` — да, 41–50 с. Но ваши три меры бьют мимо цели.**
- `enableFFTokens` ускоряет только генерацию (2–6 с), экономия ≤1–1.5 с.
- Переменной `ONNX_GENAI_INTRA_OP_THREADS` в ONNX GenAI 0.20.0 **нет**. Есть ключ `intra_op_num_threads` в `genai_config.json`. Прогнал A/B: `intra_op_num_threads=6, inter_op=1` → prefill **37.6–40.2 с** против **36.2–43.0 с** в базе. Эффекта нет: ORT и так берёт ~6 физических ядер, участок упирается в память.
- int8 вместо int4 — не первым шагом: весит вдвое больше, выигрыш не гарантирован, требует скачивания другой модели.
- **Реальный рычаг — 1 838 токенов промпта.** Это ~6 280 символов: системные правила с 5 few-shot примерами + JSON-схема инструментов (`ToolDefinitions.cs`, ~2 900 символов). Prefill масштабируется линейно: сокращение до ~850–950 токенов даёт ~19–22 с вместо ~39 с.

**2. `whisper_ms > 20 с` — нет, 12.8–17.8 с.** Но важнее другое: **время почти не зависит от длины клипа** (3.2 с → 17.8 с; 4.5 с → 13.0 с) — Whisper всегда считает окно 30 с. Поэтому VAD и обрезка тишины latency не уменьшат (на фронте уже стоит лимит 30 с). Единственный рычаг — меньшая модель: small ≈ 2.5–3× быстрее, base ≈ 4–5×.
A/B по потокам: `WhisperThreads=6` → 13 178 / 16 268 мс против 13 014 в базе. Тоже не рычаг.

**3. `total >> whisper + llm` — нет.** Расхождение <3 мс на WAV. Декод webm/opus через Media Foundation не замерен (нет webm-сэмпла без ffmpeg), но WAV-декод 2–192 мс, так что канал преобразования не узкое место. Перезагрузки модели во время запросов нет — 19 с только на старте процесса (актуально при `dotnet watch`, для замеров запускать `dotnet run --no-build`).

## 4. План оптимизации

Порядок — по (эффект ÷ риск).

**Шаг 1. Диета промпта — самый большой выигрыш, минимальный риск.**
Сократить `BuildSystemPrompt`: убрать 5 few-shot примеров (≈1 100 символов), сжать правила, убрать из `ToolsJson` описания, дублирующие правила, — цель 850–950 токенов. Проверка: фиксированный набор из 10–15 фраз (выбор инструмента + аргументы) до/после; повторный замер `prompt_tokens`/`prefill_ms`.
Ожидание: prefill ~39 с → **19–22 с**.

**Шаг 2. Whisper medium → small (int8/q8).** Medium 769M → small 244M. Проверка: те же 10–15 фраз, сравнить распознанный текст (WER вручную).
Ожидание: 13–18 с → **4–5 с**. Если качество просядет — base (ещё быстрее, но риск выше).

**Шаг 3. `enableFFTokens: true` в `SetGuidance`.** API есть в 0.20.0 (`GeneratorParamsSetGuidance(..., enable_ff_tokens)`). Одна строка, batch=1/beam=1 соблюдены. Ожидание: decode −0.5–1.5 с.

**Шаг 4 (эксперимент, наибольший потолок). Переиспользование KV-префикса.**
В 0.20.0 есть `Generator.RewindTo` + `AppendTokens`. Держать один `Generator` с уже прогретым системным промптом, на запрос делать `RewindTo(prefixLen)`, дописывать только текст команды и генерировать. Тогда prefill — только 20–40 токенов пользователя (~0.5–1 с) вместо 1 838 (~39 с). Нужно: инвалидация при смене даты в промпте, восстановление генератора после исключения, проверка, что guidance-парсер корректно откатывается по `RewindTo`. Изменение локализовано в `OnnxLlmFunctionCaller` (архитектура и интерфейс не меняются), но это уже не «минимальная правка» — делать за фича-флагом и с A/B.

**Шаг 5 (опционально).** int8-вариант Phi-4-mini — только убедившись, что шаги 1 и 4 не достаточны.
