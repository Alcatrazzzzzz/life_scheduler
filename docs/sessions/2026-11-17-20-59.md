# Сессия 2026-11-17 20-59

ADR готов: `docs/decisions/006-recurring-events.md` (по шаблону `_template.md`, нумерация продолжает 005; индекс ADR в проекте нигде не ведётся, править больше нечего).

**Что зафиксировано:**
- **Контекст** — дел на повторе много, календарь уже запрашивает диапазоном, данные одноразовых записей терять нельзя.
- **Решение** — `Recurrence` (`None/Daily/Weekly`) как колонка `ScheduleEntry` (плюс миграция `AddScheduleRecurrence`), `Date` = seed, серия бессрочная; разворачивание на сервере в `ListSchedule` в пределах `from`–`to`; общий `Id` у вхождений; правка и удаление — вся серия; в JSON — camelCase-строки.
- **Альтернативы** — отдельная сущность правила, материализация вхождений, разворачивание на клиенте, хранение `RRULE`, заранее созданная серия на горизонт, опциональная дата окончания — с причиной отказа каждой.
- **Последствия** — плюсы (одна колонка, серия одной строкой, единая точка разворачивания) и честные минусы (составной ключ `id`+дата, PUT без поля снимает повторение, нет исключений для одного дня, смена даты сдвигает день недели, разворачивание в памяти, контракт не описан в OpenAPI).
- **Когда пересмотреть** — исключения для отдельных вхождений, другие кадильности/дата окончания, объём данных, второй клиент, часовые пояса.

Кода не менял — прогонять гейты не требовалось.
